# 悦指间系统初始数据库设计

| 项目 | 内容 |
| --- | --- |
| 文档版本 | V1.0 |
| 日期 | 2026-07-29 |
| 数据库 | Microsoft SQL Server 2022 |
| 字符集/排序规则 | 中文环境使用 `Chinese_PRC_100_CI_AS_SC_UTF8`，部署前以原库实测结果确认 |
| 变更工具 | Flyway；所有 DDL、索引、基础数据和存储过程均进入 Migration |
| 依据 | 合同功能清单、旧系统 473 个 Hibernate 映射、API 和页面设计 |

旧系统已经确认使用 SQL Server，核心对象包括 `cst_customers`、`cst_membership_cards`、`cst_mc_accounts`、`cst_mc_item_suite_accounts`、`oe_bill_headers`、`oe_bill_lines` 等。新系统保留业务语义，不原样复制旧表：拆分会员、资产、账单、支付、提成和审计，去除大量 `text_attribute*` 扩展字段及映射中的公式查询。

## 1. 数据库和环境

| 数据库 | 用途 | 规则 |
| --- | --- | --- |
| `yuezhijian_legacy` | 恢复甲方旧库 | 迁移期只读，应用账号禁止写入 |
| `yuezhijian_dev` | 本地开发 | 可重建；必须通过 Flyway 创建 |
| `yuezhijian_test` | 自动化和联调 | 每次流水线从空库迁移并执行测试 |
| 预生产/生产库 | 演练和正式业务 | 禁止 `flyway clean`，上线前备份和恢复验证 |

首版使用 `dbo` schema 和模块前缀，避免一个月内引入过多 schema 权限复杂度。表前缀：`iam` 权限、`org` 组织、`cat` 商品、`mem` 会员、`ast` 资产、`apt` 预约、`trd` 交易、`inv` 库存、`vis` 回访、`mkt` 营销、`ntf` 通知、`comm` 提成、`payroll` 工资、`home` 到家、`ai` AI、`intg` 集成。

## 2. 字段和建模规则

### 2.1 类型规范

| 场景 | SQL Server 类型 | 规则 |
| --- | --- | --- |
| 主键/外键 | `bigint` | 主键默认 `identity(1,1)`；迁移不复用旧 id |
| 业务编号 | `varchar(32~64)` | 账单、预约、流水、批次等必须唯一 |
| 金额/比例 | `decimal(19,4)` | 禁止 `float/real/money`；界面通常展示 2 位 |
| 次数/积分 | `int` 或 `decimal(19,4)` | 可拆分次数时用 decimal，否则 int |
| 状态/类型 | `varchar(32)` | 代码用英文枚举，含义进入字典 |
| 中文短文本 | `nvarchar(50~500)` | 根据业务限定长度，禁止无目的 `nvarchar(max)` |
| JSON | `nvarchar(max)` | 加 `ISJSON(column)=1` 检查；只用于规则快照/第三方摘要 |
| 时间 | `datetime2(3)` | 保存 UTC；业务日期另用 `date` |
| 布尔 | `bit` | 默认值明确，不允许三态时 `not null` |
| 并发版本 | `rowversion` | 可修改聚合根必须带 `row_version` |
| 敏感值 | `varbinary`/密文 `nvarchar` | 手机、证件等使用应用层加密并另存哈希检索列 |

### 2.2 公共字段

除纯关联表和不可变流水外，可修改业务表默认包含：

```text
id bigint identity primary key
status varchar(32) not null
created_at datetime2(3) not null
created_by bigint null
updated_at datetime2(3) not null
updated_by bigint null
row_version rowversion not null
```

多门店业务表还必须包含 `biz_org_id bigint not null` 和 `store_id bigint null`。历史数据不得通过物理删除消失；基础资料使用 `status`/`disabled_at`，业务单据使用取消、作废和冲销状态。流水表为 append-only，只允许追加反向记录。

### 2.3 关键约束

- 会员手机号用 `mobile_ciphertext + mobile_hash + mobile_last4`；按手机号检索走带盐哈希，不保存明文日志。
- `trd_bill.total_receivable = sum(trd_bill_line.receivable_amount)`；结算时 `资产抵扣 + 外部实收 = 应付`，必须在同一事务校验。
- `ast_*_ledger`、`comm_ledger`、`inv_stock_ledger` 均包含 `before_balance/change_amount/after_balance` 并检查前后恒等式。
- 所有结算、充值、冲销、调账和第三方回调保存 `idempotency_key`，范围内建唯一索引。
- 报表不建立第二套可手改金额；从业务事实表计算，需要缓存时使用可重建快照。

首批必须对账：会员总数/有效数、会员卡数、储值余额汇总、积分汇总、次卡剩余次数和价值、账单数及金额、各支付方式金额、未完成预约、库存、提成和工资结果。金额与资产差异不得以“人工改库”关闭，必须记录规则、修复脚本和复核结果。

## 13. 索引、约束和数据量策略

### 13.1 必建索引

- 唯一：所有业务编号、用户账号、组织/员工/商品代码、卡号、服务码哈希、第三方事件 id、幂等键。
- 会员：`mobile_hash`、`mobile_last4`、`owner_store_id + status`、`last_visit_at`。
- 预约：`store_id + start_at + status`、`employee_id + start_at/end_at`、`member_id + start_at`。
- 账单：`store_id + settled_at + status`、`member_id + settled_at`、`bill_no`、`appointment_id`。
- 流水：`account/card/employee + occurred_at`、`source_type + source_id`、`correlation_id`。
- 报表：支付、账单行、员工分配和提成按业务日期/门店建立覆盖索引，依据执行计划调整。

### 13.2 约束

- 所有外键明确 `NO ACTION`，禁止级联删除业务历史。
- 金额、次数、比例按业务加 `check`；退款/冲销等负向业务用交易类型表达，不允许任意负数绕过规则。
- JSON 字段使用 `check (ISJSON(field)=1)`；状态字段使用应用枚举和检查约束双重控制。
- 对高并发余额/扣次使用账户行锁或乐观锁，更新账户与写流水必须在同一事务。

### 13.3 归档和保留

首版不做物理分表。`sys_audit_log`、`intg_callback_event`、短信明细和各类流水按月评估数据量；超过单表 5000 万行或明显影响 SLA 后再通过独立 Migration 引入分区。财务、资产、提成和迁移对账记录不得随普通日志清理。

## 14. Flyway Migration 规则

实际 SQL 放在：

```text
backend/src/main/resources/db/migration/
├── V202607290900__init_common.sql
├── V202607290910__init_iam_org.sql
├── V202607290920__init_catalog.sql
├── V202607290930__init_member_asset.sql
├── V202607290940__init_appointment_trade.sql
├── V202607290950__init_inventory_benefit.sql
├── V202607291000__init_visit_marketing_notification.sql
├── V202607291010__init_commission_payroll.sql
├── V202607291020__init_home_ai_integration.sql
├── V202607291030__init_migration_audit.sql
└── R__reporting_views.sql
```

规则：

1. 命名为 `VyyyyMMddHHmm__英文小写说明.sql`；时间版本全项目唯一。
2. 已在任何共享环境执行的版本文件禁止修改、改名或删除；修复只能新增更高版本。
3. `R__` 只放可重复创建的视图、函数或存储过程，不放业务表和不可逆数据修复。
4. 每个 Migration 文件顶部写需求号、变更原因、影响表、回滚/恢复方式、数据验证 SQL。
5. DDL 与数据回填分开；大表变更先演练执行时长、锁等待和磁盘增长。
6. 开发启动时执行 `flyway validate`、`flyway migrate`；CI 必须用空库从 V1 完整迁移。
7. `dbo.flyway_schema_history` 自动记录版本、描述、校验和、执行人、耗时和结果，禁止手工修改。
8. 共享开发、测试、预生产和生产禁止手工执行未归档 SQL；紧急 SQL 也要先补 Migration 和审批记录。
9. 非本地环境禁用 `flyway clean`；上线前完成全库备份和恢复演练。

每次变更的人工说明写入 `plan/migration/`，详见其中 README；说明文件与实际 SQL 版本同号，记录功能/API/页面影响、验证和部署结果。

## 15. 首版数据库完成标准

- 空库可一次执行全部 Migration，重复启动不会重复建表或重复写基础数据。
- 核心外键、唯一键、检查约束和索引已建立；API 字段与表字段能够逐项对应。
- 会员→预约→账单→结算→资产扣减→提成→回访闭环可在同一测试库运行。
- 调账、冲销、退卡和换卡均生成正反流水，原始事实不被覆盖。
- 使用旧库样例完成至少一次迁移，并对会员、储值、积分、次卡、账单和支付做数量与金额核对。
- 数据库账号按应用读写、迁移 DDL、只读报表、运维备份分权；配置中无明文生产密码。
