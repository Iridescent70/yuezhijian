# ITER-19 服务反馈与客诉处理

## 目标

落地`API-VIS-006~007`和`UI-VIS-002`，把回访中的客诉标记转为可分配、可跟踪、可解决和可复核关闭的服务反馈单。

## 已实现

- 回访记录勾选客诉后，在同一事务中自动创建一张反馈单；普通低评分不自动转客诉。
- 客诉与满意度相互独立；客户未评分时保存为空，不自动伪造为1分。
- 回访记录与反馈单一对一，重复请求不会重复建单。
- 新增服务反馈列表和详情接口，可按门店、负责人、评分、状态、反馈号、账单号和会员查询。
- 状态机为`OPEN → PROCESSING → RESOLVED → CLOSED`，支持已解决/已关闭重新打开。
- 分配、重新分配、处理备注、解决、关闭和重开全部追加处理历史。
- 负责人只能选择反馈所属门店的有效员工；解决时必须填写结果，重开时必须填写原因。
- 新增`/app/service/feedback`页面和客户服务子菜单，提供筛选、详情、会员/账单跳转及全部处理动作。

## 数据库变化

- `V202607291260__init_service_feedback.sql`建立`vis_feedback`和`vis_feedback_action`。
- `visit_record_id`唯一；评分可空且非空时限制为1至5分，状态、负责人、解决和关闭时间均有数据库检查约束。
- 新增`visit:feedback:view/manage`权限，总部管理员和店长获得权限。

## 已验证

- 端到端测试覆盖普通回访不建单、客诉回访自动建单、分配、备注、解决和关闭。
- Mapper静态测试覆盖反馈组合筛选和按预期状态更新，避免无真实SQL Server时遗漏动态SQL问题。
- `make verify`通过：后端74项测试、前端类型检查、2项单元测试和生产构建全部成功；最大公共JS约170.29 KB。

## 明确限制

- 当前反馈来源只有回访，短信、评价页和人工录入渠道待甲方确认后扩展。
- 附件、补偿金额、处理时限和超时提醒尚未接入；不能用普通备注代替财务赔付审批。
- 满意度短信识别规则属于`API-VIS-005`，不在本轮范围。
