# ITER-46 支付方式管理

## 目标

补齐合同中的付款/支付方式管理，让总部维护统一定义，门店在自身数据范围内决定是否适用、是否启用和收银显示顺序，配置结果直接作用于开单结算、充值和次卡业务的支付选项。

## 已实现

- 复用`cat_payment_method`和`cat_payment_method_store`，不重复建立支付主数据；为门店配置增加rowversion。
- 支持现金、银行卡、微信、支付宝、美团、储值支付和其他类型，以及电子支付、计入营业额、外部凭证、全局状态配置。
- 总部可新建和修改全局定义；编号创建后不可修改，历史支付始终保留名称快照和原主键。
- 总部/店长可在授权门店内切换适用、启用状态并调整完整顺序；跨店请求返回403，过期版本返回409。
- 营业端统一读取“全局启用＋本店适用且启用”的选项，配置修改立即影响结算、充值和次卡入口。
- 储值支付仍通过会员资产抵扣链路提交，后端拒绝把`STORED_VALUE`作为外部支付重复入账。
- 全局定义、门店配置和排序变化写入统一审计日志。

## 验证范围

- 门店数据范围测试覆盖本店查询成功、跨店管理拒绝。
- Mapper测试覆盖组合筛选、门店左连接、主表和门店配置rowversion更新。
- 前端类型检查、测试和生产构建纳入`make verify`。

验证结果：后端138个测试全部通过，前端2个测试、类型检查、生产构建和Compose配置检查通过；最大公共JS约175.73 KB。

## 数据库与发布

- Migration：`V202607291440__grant_payment_method_management.sql`。
- 总部管理员获得查看、全局维护和门店维护权限；店长只获得查看及本店配置权限。
- 发布后核对收银、充值、办卡、换卡中的选项顺序和启用状态，不修改既有交易快照。

## 明确限制

- 本迭代只维护业务支付分类，不保存微信/支付宝商户号、证书、密钥或回调配置。
- 真实电子通道收退款、回调验签和对账仍等待甲方沙箱资料。
- SQL Server实表Migration、rowversion和事务回滚验证等待本地Docker权限恢复。
