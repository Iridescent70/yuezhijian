# ADR-0001：首版使用SQL Server 2022

| 项目 | 内容 |
| --- | --- |
| 状态 | 本地开发已采用，生产Edition待甲方许可证确认 |
| 日期 | 2026年7月29日 |
| 影响范围 | 数据库、后端、测试、历史数据迁移和部署 |

## 背景

旧系统配置和Hibernate映射确认使用SQL Server，核心数据分布在会员、账单、预约、库存、员工、权限和统计等数百张映射表中。项目只有一个月，并要求迁移全部历史数据；此时改用其他数据库会额外增加数据类型、函数、统计SQL和备份恢复验证工作。

## 决定

1. 新系统首版使用SQL Server 2022。
2. 本地和测试环境使用Developer Edition容器；生产使用Standard或Enterprise，按数据规模、功能和甲方许可证确认。
3. 同一实例使用三个独立数据库：只读旧库 `yuezhijian_legacy`、开发库 `yuezhijian_dev`、测试库 `yuezhijian_test`。
4. 新库使用Flyway管理结构，所有SQL变化进入Git并由 `flyway_schema_history` 留痕。
5. 历史数据通过独立迁移程序读取旧库并写入新库，不允许新业务直接读写旧表。

## 未采用方案

- **PostgreSQL**：技术能力满足要求，但首月会增加跨数据库迁移及统计SQL重写风险，后续如有明确收益可单独评估。
- **SQL Server 2025**：版本更新，但本项目优先选择已成熟且支持周期足够覆盖项目维护期的SQL Server 2022。
- **继续使用旧库原表**：旧表命名、金额类型、历史字段和业务耦合较重，不利于权限、审计和后续维护。

## 影响和处理

- 后端加入微软JDBC驱动和 `flyway-sqlserver`。
- 本地Docker环境仅支持x86_64；当前开发机满足要求。
- 旧备份恢复后先执行只读抽样和兼容性检查，再做数据迁移，不直接把旧库当新库升级。
- Migration失败时停止应用发布；已执行脚本不回改，通过新版本SQL向前修复。正式发布前保留可验证备份，必要时回滚应用和数据库备份。
