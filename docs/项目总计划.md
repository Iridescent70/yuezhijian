> 说明：本计划按2026年7月29日启动、2026年8月28日完成上线验收编排，开发、测试、数据迁移和上线均包含在一个月内。该周期以既有代码可复用、需求快速定稿、人员全职并行和第三方条件按时就绪为前提；任一前提不满足时，必须通过增加资源、减少本期范围或书面调整交付日期处理，不得取消必要测试和数据核对。

## 一、项目目标

本项目同时完成两项交付：一是建设可独立运行的“悦·指间美甲管理系统”；二是在不破坏既有业务和历史数据的前提下，完成“悦指间门店管理系统”V3.0优化。

项目按“需求快速定稿 → 设计与开发并行 → 每日提测 → 分批联调 → 迁移演练 → 用户验收 → 上线归档”的路径执行，最终实现：

1. 两个系统的合同功能范围全部落地，并可按需求编号追溯到设计、开发任务、代码版本、测试用例和验收结果。
2. 打通会员建档、预约、到店、开单、结算、回访、复购，以及次卡、薪酬、统计等核心闭环。
3. 多门店、角色权限、数据范围、敏感字段、操作审计、状态流转、导入导出和异常处理符合两份需求的通用要求。
4. 财务、余额、积分、次卡、调账、冲销、提成和工资等关键数据计算准确、过程可追溯、结果可核对。
5. 完成部署、迁移、培训、运维、备份、恢复和回滚资料，具备正式上线和持续维护条件。

### 一个月交付的执行前提

1. 启动后3天内完成范围冻结、数据中心5项明细补齐、系统关系确认及财务计算规则确认，后续不新增需求。
2. 现有系统代码、数据库、部署环境和接口文档在首日完整移交，且核心基础模块可直接复用；如工作流A实际为完全从零建设，139项范围无法在一个月内按合同质量完成，须立即拆分交付批次。
3. 至少设置4个并行研发小组，分别负责A线核心业务、A线统计与配置、B线结算与会员、B线移动端与经营支撑，并配置独立测试力量。
4. 产品、研发、测试、运维和甲方关键用户全程参与，需求问题当天答复，功能完成当天提测，缺陷当天分派。
5. 短信、支付、美团、地图等第三方测试账号、白名单和联系人须在启动后3天内到位。
6. 若第3天仍有关键规则、数据、资源或接口未落实，项目经理必须提交影响评估，并在“缩减本期范围、增加资源、调整交付日”中形成书面决策。

### 2.2 范围管理原则

1. 两份经确认的功能清单及其后续书面澄清记录共同构成范围基线，口头说明不直接作为开发依据。
2. 两个系统中重复出现的会员、预约、结算、统计、系统管理等能力，先确认是否共用代码、服务、数据库和主数据，再确定复用或独立实现方案；无论是否复用，均须分别保留需求和验收记录。
3. 当前需求未明确列出的新增渠道、硬件采购、第三方服务费、历史数据治理和定制报表，先进入变更池，不直接占用本期排期。
4. 站内通知属于V3.0本期范围；短信、微信公众号等后续扩展渠道仅在双方书面确认后纳入。
5. 第三方短信、支付、美团核销、地图定位等功能，以甲方按计划提供账号、接口权限、测试环境和合规材料为前提。

## 六、关键业务与接口要求

1. **统一业务对象**：明确门店、员工、会员、预约、账单、支付、储值、积分、次卡、券码、服务码、提成、工资、调账、冲销和消息的唯一标识、归属关系和状态。
2. **统一计算口径**：对金额精度、四舍五入、优惠分摊、退款、退卡、换卡、跨月冲回、负向提成、借调业绩、第三方分润、朋友消费和客流统计建立可执行的规则表及“黄金样例”。
3. **接口契约**：每个接口写清调用方、提供方、认证、字段、枚举、幂等、超时、重试、错误码、审计、样例和验证方法；接口变化须经过评审并同步用例。
4. **文件与任务**：导入、导出、报表和批量任务采用可追踪任务号；文件访问继承数据权限和脱敏规则，失败时返回可定位原因。
5. **第三方集成**：短信、支付、美团核销、地图定位等分别建立测试账号、回调白名单、限流、失败补偿、对账和降级方案，不用生产账号替代测试。
6. **跨端一致性**：PC端、移动端和到家服务共用的会员、预约、账单及权限状态应保持一致；禁止通过人工改库完成正常业务流转。

## 七、数据迁移与上线切换

1. M0完成数据源清单和质量抽样，识别重复会员、无效手机号、余额异常、孤立账单、卡项不一致、门店和员工归属缺失等问题。
2. M0确认字段映射、清洗规则、历史范围、停机窗口、增量策略、敏感信息处理和数据责任人。
3. 8月21日前完成第一次全量迁移演练，8月25日前完成第二次全量迁移演练；每次记录数据量、耗时、失败项、关键资产差异及修复结果。
4. 迁移后按会员数、有效卡数、储值余额、积分、次卡剩余、未结账单、门店营业额和员工提成等关键维度对账；差异必须可解释、可复现、可审批。
5. 上线前完成全量备份和恢复验证；切换失败、对账不通过或核心流程异常时，按书面方案回滚，不在生产库直接修数。
6. 工作流B涉及既有系统变更，数据库结构调整必须提供可回退脚本，并验证历史账单、报表和工资归属不受停用、停售或规则升级影响。

为满足一个月内完成139项范围的并行排期，建议配置项目经理1名、产品/业务分析2—3名、技术负责人1名、4个独立研发小组、测试4—6名，以及共享的UI、数据和运维人员，整体建议不少于25人全职投入。M0根据代码复用程度和功能估算确定最终投入；若研发和测试资源明显不足，必须缩减本期范围或调整交付日期，不以压缩测试、迁移和上线验证换取表面进度。

## 十、沟通与进度机制

1. **每日站会**：每天上午控制在15分钟内，各负责人只汇报已完成、今日计划、风险阻塞和所需支持。
2. **每日质量检查**：每天结束前更新需求完成率、当日提测率、测试通过率、缺陷存量和第二天交付项；问题不过夜。
3. **每周项目会**：汇总范围完成率、测试通过率、缺陷趋势、风险依赖和下周目标，形成书面周报。
4. **里程碑评审**：由项目经理组织产品、研发、测试、运维和甲方业务负责人按完成标准逐项签字，不以演示代替验收证据。
5. **统一问题表**：每个问题记录编号、描述、影响系统、严重程度、负责人、计划日期、当前状态和关闭证据。
6. **统一完成口径**：功能完成必须同时满足需求明确、代码合入、评审通过、环境部署、测试通过和文档更新；仅完成编码不计为完成。

## 十二、变更、质量与执行规则

1. M0后新增或修改需求须提交变更单，说明原因、业务价值、影响模块、工作量、风险、费用和里程碑影响，经双方批准后进入排期。
2. 公共字段、状态、接口和计算口径变化时，必须同步更新原型、规则表、数据库/接口说明、代码、测试用例和培训资料。
3. AI生成的代码必须由对应研发负责人审查并在目标环境实际运行；生成完成不等于交付完成。
4. 测试团队负责发现、记录和复测问题，不直接绕过研发流程修改生产代码或生产数据。
5. 主流程、金额与权益准确性、权限越权、数据丢失等问题优先于界面优化和新增建议。
6. 每个发布版本必须有唯一版本号、变更记录、数据库脚本、配置说明、测试报告、部署步骤和回滚方案。
7. 任何延期均记录原因、影响范围、责任/协作角色、恢复措施和新的承诺日期，作为计划变更和验收依据。

## 十四、项目完成标准

项目同时满足以下条件后方可判定完成：

1. 两个系统均可按批准的部署方案独立启动、访问、备份、恢复和升级。
2. 所有确认范围均已交付，需求—设计—任务—代码—测试—验收链路完整，覆盖率100%。
3. 会员到复购、预约到结账、次卡全生命周期、薪酬提成结算、基础资料到报表等核心闭环全部通过。
4. 财务、会员资产、权益、薪酬、营业额和迁移数据无未解释差异，关键操作可审计。
5. 权限、安全、性能、兼容、迁移、回归和UAT达到双方确认的准入标准，阻断和严重缺陷为0。
6. 甲方人员可根据手册独立完成日常操作、基础配置、查询导出和常见异常处理。
7. 上线稳定期完成，源代码、版本、测试证据、数据资料、部署运维资料和已知问题全部归档。
8. 双方完成最终验收签字；遗留事项如存在，均有书面范围、负责人和完成日期。

## 十五、技术实施基线

项目技术选型、总体架构、数据库规则、初始目录、统一命令、一个月技术执行步骤、CI/CD和质量门槛，以 [《技术实施计划》](../plan/技术实施计划.md) 为执行基线。

首版推荐采用Java 25 LTS、Spring Boot 3.5.x、MyBatis、Vue 3、TypeScript、uni-app、PostgreSQL 17、S3兼容对象存储、Nginx和Docker Compose，整体采用单仓库、前后端分离、模块化单体架构。首月不拆微服务，不引入Kafka、Elasticsearch、Redis集群或Kubernetes。

后续迭代必须在 `plan/iterations/` 建立迭代计划；技术基线变化必须在 `plan/decisions/` 建立ADR并同步更新技术实施计划。
