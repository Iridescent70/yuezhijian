# 悦指间基于芋道 Vue3 管理端的重构迁移方案

更新时间：2026-07-30。

## 1. 重构目标

本次重构不推翻 `main` 已完成的业务后端和数据规则，而是替换 PC 管理端底座，并利用芋道现成的布局、动态路由、权限指令、表格表单、文件、消息、日志、报表和业务模块页面降低重复开发量。

迁移基线：

- 业务基线：`main@6cae2c8`，包含 `ITER-00` 至 `ITER-52` 的代码与记录。
- 新前端底座：`yudaocode/yudao-ui-admin-vue3@9445977`。
- 重构分支：`refactor/yudao-foundation`。
- 后端继续使用 `backend/` 中的 Java 21、Spring Boot 3.5、Spring Session、MyBatis、Flyway 和 SQL Server 实现。
- 新前端统一在 `frontend/` 开发；原自研前端保存在 `ref/main-frontend-snapshot/` 供迁移对照。
- 甲方旧系统源码继续只读保存在本地 `ref/legacy-source/`，不纳入 Git。

## 2. 不可丢失的业务资产

以下内容不能因为更换前端底座而重新猜测或降级：

- `docs/` 两份合同功能清单和项目总计划。
- `plan/` 中的 API、页面、数据库、技术决定、Migration 说明和 52 个迭代记录。
- `memory/` 中已经冻结的金额、资产流水、冲销、门店范围、敏感字段、异步任务和状态机规则。
- `backend/` 已实现的会员、预约、账单、结算、会员资产、次卡、代金券、提成、回访、主数据、审计、通知和礼品库存能力。
- `backend/src/main/resources/db/migration/` 中的 44 个 SQL Server Flyway Migration。
- 甲方旧源码中的历史页面、字段、`.do` 入口和 Hibernate 映射参考。

“芋道已有类似页面”不等于可以替换悦指间业务规则。芋道模块主要复用交互、组件和通用平台能力，资金、权益、库存和提成仍以悦指间后端状态机为准。

## 3. 芋道复用映射

| 悦指间范围 | 芋道可复用点 | 处理策略 |
| --- | --- | --- |
| 登录、用户、角色、菜单、数据权限 | `system/user`、`role`、`menu`、权限指令、动态路由 | 复用前端框架；继续使用现有 Spring Session、CSRF、门店范围和权限码，建立兼容适配层 |
| 门店、员工、职务 | `system/dept`、`user`、`post` 页面模式 | 复用树表、表单和选择器；门店切换、员工隐私和行版本规则保留 |
| 通知、短信、操作日志 | `system/notify`、`sms`、`operatelog`、`loginlog` | 高复用；先适配现有站内信和审计 API，再接短信渠道 |
| 文件、异步任务、下载中心 | `infra/file`、`job`、上传与分页组件 | 复用组件；对象权限、保留期、租约和结果清理由现有后端负责 |
| 会员、等级、标签、分组 | `member/user`、`level`、`tag`、`group` | 复用页面结构；会员资产、手机号保护、归属调整和批量操作使用现有接口 |
| 产品、服务、分类、单位 | `mall/product`、`erp/product`、`wms/md` | 复用列表、规格和主数据交互；门店价格、上下架和历史追踪保留 |
| 礼品与产品库存 | `wms/inventory`、`erp/stock` | 复用库存查询和单据页面模式；礼品库存、调拨、盘点流水继续使用现有状态机 |
| 开单、支付、退款、冲销 | `mall/trade`、`pay/order`、`refund` | 只复用展示和支付组件；混合支付、会员资产扣减、整单冲销和对账规则不替换 |
| 预约、回访、服务反馈、到家服务 | 通用表单、日历、BPM、地图组件 | 预约和到家业务定制；审批场景评估逐步接 BPM，不直接改写现有审批事实 |
| 统计、数据中心、工资单 | ECharts、报表设计器、大屏组件 | 复用展示能力；指标口径、门店范围和导出脱敏必须先确认 |
| AI 推荐、在线试色 | AI 页面框架、文件与富媒体组件 | 仅复用框架；模型、输入字段、图片规则和验收口径由甲方确认后实现 |

## 4. 迁移阶段

### P0：新底座可运行

- 完成芋道源码导入、品牌和构建脚本调整。
- 适配现有 `/api/v1` 响应格式、Spring Session Cookie 和 CSRF Token。
- 把当前用户、角色、权限和菜单转换为芋道动态路由结构。
- 接入真实工作台；未迁移业务页面显示明确的迁移状态，不伪装成已完成。
- 增加当前门店切换、会话续期和退出验证。

### P1：迁移 main 已完成页面

按业务风险和依赖顺序迁移：

1. 组织门店、角色、员工、职务、工位和基础字典。
2. 会员主档、标签、归属调整、储值/积分/次卡资产。
3. 预约、账单、混合结算、优惠、冲销和退卡审批。
4. 产品、服务、分类、单位、支付方式和操作历史。
5. 回访、服务反馈、系统参数、下载中心、通知公告。
6. 礼品库存、调拨、盘点和线上试色。

每个页面迁移必须同时完成权限、门店范围、错误码、并发版本、空状态和关键业务测试，不能只完成视觉搬运。

### P2：完成合同尚未开发范围

- 积分兑换与库存原子扣减。
- 服务档案、咨询卡、常用色号和赔付审批。
- 完整薪酬规则、多人分配、店长提成和工资单。
- 短信发送、上行回调、生日/到期/日报等通知任务。
- 到家服务订单、派单、技师端和客户端。
- 统计分析、数据中心及甲方确认后的 AI 推荐。

### P3：上线迁移与验收

- 甲方旧库备份盘点、字段映射、清洗规则、试迁移和逐项对账。
- 权限、敏感字段、资产余额、不可变流水、报表口径和导出文件验收。
- 灰度、回滚、停机窗口、最终增量迁移和上线签字。

## 6. 验收原则

- “代码存在”不等于“迁移完成”；必须在芋道新前端中可访问并通过真实后端验证。
- memory profile 只能用于自动化隔离，SQL Server 持久化和重启复查仍是业务完成证据。
- 金额、余额、积分、次卡、库存、提成和退款必须有对账结果。
- 未确认的甲方规则保留为显式 TODO，不使用芋道示例数据或默认规则冒充业务实现。
